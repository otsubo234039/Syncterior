# 共同編集APIの接続仕様（提案）

Issue #8のフロントエンド実装が想定するAPIです。**このリポジトリには、以下のAPIを提供するサーバーはまだありません。** エンドポイント・保存方法・サーバー技術の決定や実装は別途必要です。

## 接続設定

`frontend/.env.example`を参考に`.env.local`を作成します。

```dotenv
VITE_ROOM_API_URL=/api
```

これは接続先の指定であり、APIやViteのプロキシを生成する設定ではありません。同じオリジンの場合は、リバースプロキシなどで`/api`を実際のサーバーへ転送してください。別オリジンの場合は`https://example.com/api`などのベースURLを指定し、API側でフロントエンドのオリジンからのJSONリクエスト・プリフライト・SSEを許可する必要があります。環境変数変更後は開発サーバーを再起動し、本番環境では再ビルドしてください。

同じビルドを複数環境で使う場合は、アプリのmoduleスクリプトより前に`globalThis.SYNCTERIOR_CONFIG = { roomApiUrl: "/api" }`を設定できます。文字列があればビルド時設定より優先し、空文字列ならAPIを無効にします。省略時は`VITE_ROOM_API_URL`へフォールバックします。これはブラウザへ公開される設定なので秘密情報を入れないでください。設定は起動時に読み取るため、変更後はページを再読み込みします。配信側での設定注入・API実装は別途必要です。

未設定の場合、個人編集は通常どおり動作します。共有ダイアログには利用できない旨を表示し、リンクの新規発行は無効にします。共有リンクを開いた場合も、個人用の初期配置を共有データとして送信しません。

## 共有するデータ

家具の配置と間取りを共有します。選択中の家具、カメラ位置、寸法表示のON/OFFは各参加者のローカル状態です。

部屋のスナップショット例:

```json
{
  "id": "0123456789abcdefghijklmnopqrstuv",
  "revision": 12,
  "planVersion": 0,
  "planKey": "studio",
  "items": [
    {
      "id": "sofa-1",
      "type": "sofa",
      "name": "2人掛けソファ",
      "w": 1.6,
      "d": 0.82,
      "h": 0.78,
      "color": "#9eab9a",
      "x": 0,
      "z": 0,
      "rot": 0
    }
  ],
  "appliedOperationIds": ["確定した操作のID"]
}
```

- `id`: サーバーが生成する32文字の推測困難なID。文字種は英数字・`_`・`-`です。リンクの所持を編集権限として扱うため、単なる連番にはしません。
- `revision`: 部屋の変更順を表す0以上の整数。受理した操作ごとに増加し、クライアントは古いrevisionを無視します。
- `planVersion`: 間取りの置き換えごとに増加する0以上の整数。旧間取りに対する未送信操作を新しい間取りへ適用しないために使います。
- `planKey`: `studio` / `1ldk` / `family`。
- `items`: 家具の配列。最大200点。IDは部屋内で一意にします。寸法と座標はメートル、回転はラジアンです。
- `appliedOperationIds`: 確定済みの操作ID。楽観的に表示した変更を二重に適用しないため、未確認の操作が含まれるように応答・配信してください。現行クライアントでは確定済みIDの全件を返す仕様を想定します。件数増加時にはサーバー側とクライアント側を合わせて確認方式を見直してください。

全てのスナップショット応答・SSEのstateイベントで同じ形式を返します。サーバー側でも家具の種類、寸法、座標、色、操作内容、件数を検証してください。フロントエンドの検証はAPI側の検証を代替しません。

## エンドポイント

以下はベースURLに続くパスです。

| メソッド | パス | 用途 |
| --- | --- | --- |
| POST | `/rooms` | 現在の配置から共有部屋を作成 |
| GET | `/rooms/:id` | 最新の部屋を取得 |
| POST | `/rooms/:id/operations` | 一つの操作を適用 |
| GET | `/rooms/:id/events` | SSEで配置と参加人数を受信 |

### 部屋を作成する

`POST /rooms`に`{ "planKey": "studio", "items": [...] }`を送ります。成功時は201または200でスナップショットを返してください。

成功後、フロントエンドはURLの`room`クエリに部屋IDを設定します。例: `https://example.com/?room=0123456789abcdefghijklmnopqrstuv`。リンクのコピーはユーザー操作で行い、失敗した場合はリンク欄を選択して手動でコピーできるようにします。

### 操作を送信する

`POST /rooms/:id/operations`のリクエスト例:

```json
{
  "id": "クライアントが生成する一意の操作ID",
  "planVersion": 0,
  "operation": {
    "type": "update",
    "id": "sofa-1",
    "patch": { "x": 0.5, "z": -0.2 }
  }
}
```

| type | その他のフィールド | 動作 |
| --- | --- | --- |
| `add` | `item` | 家具を追加 |
| `update` | `id`, `patch` | 指定家具の`x`・`z`・`color`の指定項目だけ変更 |
| `rotate` | `id` | 現在の向きから90度回転 |
| `remove` | `id` | 指定家具を削除 |
| `change-plan` | `planKey`, `items` | 間取りと初期家具を置き換え、planVersionを増加 |

- サーバー側で操作を直列化し、最新の状態に適用してください。部屋全体の上書き方式では別々の家具への変更が消えてしまいます。
- 同じ家具の同じプロパティを同時に操作した場合は、サーバーが後から受理した値を採用する想定です。家具の占有ロックやカーソル表示は今回の対象外です。
- `rotate`は差分操作です。同時回転を固定角度の上書きで取り消さないでください。
- 同じ操作IDの再送は冪等に扱い、二重に適用しないでください。回線切断で応答を受け取れない場合に再送します。
- 遅れて届いた移動・回転・削除の対象家具が既にない場合、家具を再生成せずに操作を確定してください。
- 成功時は200で最新のスナップショットを返し、その操作IDを`appliedOperationIds`に含めてください。全参加者へstateイベントも配信してください。
- フロントエンドは自分の操作を即時表示し、未送信の連続した位置変更をまとめて送信します。確認済みの状態に未確定の操作を重ねるため、他の家具への変更も受け取れます。

### リアルタイム配信

`GET /rooms/:id/events`は`Content-Type: text/event-stream`で接続を維持します。接続直後と再接続時は、最新のスナップショットを必ず送ってください。

```text
event: state
data: {"id":"...","revision":12,"planVersion":0,"planKey":"studio","items":[],"appliedOperationIds":[]}

event: presence
data: {"participants":2}

```

例中のstateは構造説明用です。実際の`id`は32文字で送信してください。

参加人数は自分の接続を含む1以上の整数です。退出・切断後にも更新してください。フロントエンドは人数を受信するまで推定値を表示しません。SSEのタイムアウトを防ぐハートビートやプロキシのバッファリング設定はサーバー側で対応してください。

切断中は編集を止め、最後に確認した配置を表示します。EventSourceによる再接続と「再接続」操作に対応し、操作送信に失敗した場合も再接続を試みます。再取得した状態で確定済み操作を除外してから未送信操作を再送します。

## エラー

JSONで`{ "error": "表示可能な日本語メッセージ" }`を返してください。

| ステータス | 想定 |
| --- | --- |
| 400 | 不正な操作・件数超過。対象操作を取り消してエラーを表示 |
| 404 | 部屋が存在しない。編集を停止して退出・再接続を案内 |
| 409 | 間取りの世代が不一致。`snapshot`に最新スナップショットを付ける |
| 5xx / 通信エラー | 未確認操作を保持し、再接続後に再送 |

部屋の保存期間、永続化方法、認証、共有リンクの失効や権限変更、サービス配置はサーバー実装時の決定事項です。現状のフロントエンドだけでは別端末間の同期や永続保存は動作しません。

## 家具の回転と境界補正（Issue #13）

`update`と`rotate`の確定結果は、最新の回転角θに対してXZ平面の外接矩形の幅`|w cosθ| + |d sinθ|`、奥行`|w sinθ| + |d cosθ|`を求め、その半分を部屋の各辺から差し引いた範囲へX/Z座標を制限します。寸法w/dは未回転の値を保持します。境界は既存と同じ部屋中心から±幅/2・±奥行/2です。

壁際の回転は、はみ出す軸だけ最寄りの位置へ補正し、中央へリセットしません。外形が部屋より大きくなる操作や非有限の数値は適用せず、元の家具を維持します。直角回転の丸め誤差には1e-10mまでの許容を設けます。追加・読み込み時の不正データや寸法上限のサーバー検証は引き続き必要です。

サーバーは同じ規則で確定snapshotを生成し、未回転寸法の制限や未補正の座標を返して、クライアントの補正を取り消さないでください。テスト専用APIでは四隅から独立に補正して検証します。実バックエンドでの適用は未実装です。

## 個人配置のブラウザ内保存との分離（Issue #18）

個人用ページではバージョン付きlocalStorageから配置を復元し、個人操作時だけ保存します。共有リンクではこの保存を初期配置として送信せず、共有APIの取得結果を表示します。共有の確定結果・未確定操作・再接続・退出はlocalStorageを更新しません。退出後の確定配置を個人として編集した場合だけ個人保存を更新します。APIの要求形式に変更はなく、ブラウザ内保存はサーバー永続化の代替ではありません。
