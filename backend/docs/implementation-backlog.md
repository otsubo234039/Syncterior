### BE-01: 実行環境・開発基盤

`backend/`に依存関係定義・ロックファイル・アプリケーションの起動入口・テスト設定を追加します。Node.js / Lambdaは#4の案です。採用するランタイムとバージョンを明記し、ローカルでAPIを起動する方法を用意してください。必要な環境変数は実値を含めず`.env.example`などで共有します。

完了条件: 新しい開発環境でREADMEに沿ってセットアップ・起動・テストができること。

### BE-02: 部屋の作成・取得・永続化

現在の間取り・家具配置から共有部屋を作成し、推測困難なIDで取得できるようにします。フロントエンドの現行案では、部屋IDは英数字・`_`・`-`からなる32文字で、URLの`room`クエリに入ります。ID形式を変える場合はフロントエンドの検証も変更します。

保存対象は間取り・家具と同期用メタデータです。選択中の家具、カメラ位置、寸法表示のON/OFFは各画面のローカル状態であり、共有しません。DynamoDBを使う場合は、部屋・操作履歴・接続情報のキー設計と保持期間を決めてください。

Issue #18の個人配置保存はブラウザ内のlocalStorageだけで完結します。共有の取得・同期・未確定操作・退出は個人保存を更新しません。退出後の配置を個人として編集した時点で保存します。サーバーへの保存・端末間復元はBE-02として引き続き未実装で、ブラウザ内復元のテストだけでは完了としません。

完了条件: 同じリンクから同じ配置を取得でき、決定した保持・復元方針を満たすこと。存在しない部屋と期限切れの扱いが定義されていること。

### BE-03: 家具・間取りの操作API

フロントエンドの案は、部屋作成`POST /rooms`、取得`GET /rooms/:id`、操作`POST /rooms/:id/operations`です。ベースURLや詳細なJSON形式は[接続仕様案](../../frontend/docs/collaboration-api.md)を参照してください。

受理する操作は`add`、`update`（X/Z位置・色）、`rotate`（90度の差分回転）、`remove`、`change-plan`（間取りと家具の置き換え）です。部屋全体を毎回上書きせず、最新状態に指定操作を適用してください。

完了条件: 各操作の結果をスナップショットとして取得できること。遅れて届いた移動・回転で削除済み家具が復活しないこと。

### BE-04: 操作順序・競合・重複排除

更新順を示す`revision`、間取りの世代を示す`planVersion`、再送を識別する操作IDを扱います。異なるLambda等が同時に更新しても変更が消えないよう、条件付き更新・トランザクション等の整合性を確保する方式を設計してください。

同じ操作IDは一度だけ適用し、回転の二重適用を防ぎます。間取り変更後に旧世代の操作が届いたら、新しい部屋へ適用せず最新状態と競合エラーを返してください。現行クライアントは`appliedOperationIds`で確定済み操作を認識します。履歴が増える場合の保持・確認方式を変えるときは、クライアントも合わせて更新する必要があります。

完了条件: 別家具への同時変更が両方残り、同じ項目の競合でも全クライアントが同じ状態に収束すること。再送・応答順の逆転・間取り変更のテストがあること。

### BE-05: リアルタイム配信・参加人数

接続直後・再接続時に最新の配置を送り、受理した変更を同じ部屋の参加者へ配信します。現在のフロントエンド案は`GET /rooms/:id/events`のSSEで、`state`と`presence`イベントを受け取ります。WebSocketを採用する場合は同等の情報を送り、フロントエンドの接続処理も調整してください。

接続情報を部屋単位で管理し、参加・退出・切断・接続期限切れを処理します。参加人数は自分を含みます。再接続時の重複カウント、古い接続情報の残存、別の部屋への誤配信を防ぎます。

完了条件: 2端末で配置が同期され、参加人数が接続・切断に追従すること。切断中に未確認だった操作を安全に再送できること。

### BE-06: 入力検証・エラー・接続設定

#4ではZodによる検証を提案しています。家具の種類・一意なID・寸法・座標・回転・色・件数、操作の許可フィールドをサーバー側でも検証してください。現行クライアントの家具上限は200点です。

**部屋の中心が原点なのでX/Z座標の負数は正常です。** #4にある「負の座標を拒否する」案は現在のモデルと整合しません。負数そのものではなく、数値の有限性・部屋の範囲・家具の寸法等を検証します。Issue #13でフロントエンドは回転後の外接矩形を使う境界補正を実装しています。移動・数値入力・回転時は、はみ出す軸だけ最寄りの位置へ補正し、部屋に収まらない回転は元の家具を維持します。BE-03でも同じ規則を適用して確定snapshotを返す必要があります（未実装・実サーバーとの結合未確認）。詳細と丸め誤差の扱いは[接続仕様](../../frontend/docs/collaboration-api.md#家具の回転と境界補正issue-13)を参照してください。

現行案は400（不正な操作）、404（存在しない部屋）、409（間取りの世代不一致。最新snapshotを添付）、5xx（サーバー障害）を区別します。JSONのエラー本文、許可するオリジン、プリフライト、HTTPS、APIのベースURLを定義します。

完了条件: 不正な入力が保存されず、フロントエンドが失敗理由を識別できること。同一・別オリジンの採用構成で接続できること。

### BE-07: 認証・共有権限の管理

#4にはCognito User Pool、メール・パスワード、クライアントシークレットを持たないブラウザ用クライアントの案があります。現行フロントエンドにはログインUIや認証トークンの送信処理がありません。

ログインと共有リンクの関係を先に決定してください。部屋の所有者・リンク参加者ができる操作、リンクの保持期間、認証が必要なAPIを定め、サーバー側で権限を検証します。閲覧専用ロール・リンク失効UIなどを追加する場合は別途範囲を決めます。

完了条件: 決定したアクセス制御をAPI側で適用し、フロントエンドの参加フローと矛盾がないこと。

### BE-08: IaC・CI/CD・運用監視

#11の案はTerraform、S3 / DynamoDBによるtfstate管理、GitHub Actions、CloudWatchです。採用構成に沿って環境分離、配置手順、必要権限、設定値の管理を用意します。同期エラー・接続数・配信失敗を調査できるログと監視を整備してください。

完了条件: 手順に沿って環境を構築・更新でき、テストと配置の実行方法が明記されていること。共有リンクの秘密部分や認証トークンをログへ不要に記録しないこと。

### BE-09: Gemini API連携

#4にはLambdaからGemini APIを呼び出し、キーをSSM Parameter Storeの暗号化された値で管理する案があります。入力・出力、UI、利用目的、エラー時の動作は未定義です。共同編集APIとは分け、機能仕様を決めてから実装します。

完了条件: 合意した機能の入出力・API・エラー処理・検証手順があり、秘密情報をフロントエンドやリポジトリへ含めないこと。

### BE-10: 結合・同時編集・負荷テスト

P0では実サーバーに接続した2クライアントの共同編集を検証します。フロントエンド内のAPIアダプターによるユニットテストや、`frontend/e2e/fixtures/room-api-server.js`を使うブラウザE2Eだけで完了としないでください。これらはテスト専用の応答であり、本番バックエンドの動作確認ではありません。P1では#11のk6 / Artillery等の案を基に、想定同時接続数・更新頻度・許容遅延を決めて負荷を確認します。

最低限の結合シナリオ:

- 同じリンクから参加し、追加・移動・回転・削除・色変更・間取り変更が相手へ反映される。
- 別々の家具への同時操作、同じ項目への競合、連続回転が正しく確定する。
- 削除後の遅延操作や旧間取りへの操作で家具が復活しない。
- 切断・応答消失・再接続で操作が失われたり二重適用されたりしない。
- 存在しない部屋、不正な入力、サーバー障害を画面が識別できる。
- 別の部屋に変更が漏れず、参加人数が退出・接続期限切れに追従する。

完了条件: 自動テストと実接続の確認結果を残し、未検証の環境・負荷条件を明示すること。
