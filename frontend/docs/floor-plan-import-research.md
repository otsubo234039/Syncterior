# 間取り画像から編集可能な3Dの枠を作るための調査

調査日: 2026-11-06。Issue #28の任意画像取り込み、概算寸法の数値調整、将来の1/n表示を対象とする。フロントエンドだけで成立する方法を優先する。

## 結論

今回の第一候補は、ブラウザ内の画像処理で壁候補を抽出し、利用者が画像に重ねて修正・寸法調整してから、既存のReact Three Fiberで3D化する構成。

OpenCV.jsは画像処理部分の導入候補。Blueprint3Dは壁・頂点・部屋を編集する設計の参考になる。どちらも、任意の間取り画像から壁・ドア・窓を完全に認識する単体ライブラリではない。自動認識を強める場合はCubiCasa5Kなどの学習モデルが候補だが、利用条件、推論環境、今回の日本語図面での品質を別途検証する必要がある。

この結論は公式ドキュメント・公開実装と現在のコードを比較した設計上の判断。その後OpenCV.jsを実装し、4画像での抽出・数値調整・保存・復元をデスクトップ幅のブラウザで確認した。他のライブラリや学習済みモデルとの実行比較は行っていない。

[FloorplanVLM（2026年2月）](https://arxiv.org/abs/2602.06507)は、画像から間取りの構造を表すJSONを生成する研究。斜めの壁や曲線も対象としており、中間データをJSONにする方針の参考になる。

## #28に反映する設計

1. 画像読み込み・認識、編集用の間取りデータ、3D描画を分離する。認識処理が返すのは壁候補・輪郭で、直接Three.jsのMeshを作らない。
2. OpenCV.jsを評価する場合は、[モルフォロジー処理](https://docs.opencv.org/4.x/d4/d76/tutorial_js_morphological_ops.html)と[HoughLinesP](https://docs.opencv.org/4.x/d3/de6/tutorial_js_houghlines.html)を組み合わせる。同じ4画像で欠落・誤検出・接続切れ、初回ダウンロード量、処理時間を現行試作と比較してから採否を決める。現時点で速度や精度が改善したとは判断しない。
3. 壁の端点、床の多角形、開口部の位置・幅・高さをメートルで保存する。認識結果は画像へ重ねて表示し、手動追加・削除・数値修正を可能にする。
4. 長さの基準がない画像から実寸を確定しない。既知の壁の長さ、または全体寸法を利用者が入力して補正する。畳数や部屋名のOCRは初期実装の必須条件にしない。
5. 床・壁の立体化には既存のThree.jsを使う。[Shape / ExtrudeGeometry](https://threejs.org/docs/pages/ExtrudeGeometry.html)で輪郭を立体化できる。ドア・窓は周辺の壁を分割する方法でも表せるため、最初から別のCSGライブラリは必須ではない。
6. 実寸のデータと表示倍率を分ける。1/n表示でも保存する寸法は変えない。画面上の物理的な縮尺を保証するには、画面サイズ等の校正が別途必要。
7. AIモデルを後から採用する場合も同じ編集用データへ変換し、既存の数値調整・検証・描画を再利用する。サーバー推論が必要なら、フロント実装とは別にバックエンドの要件とIssueを整理する。

## OpenCV版の実装記録

`@techstark/opencv-js@4.12.0-release.1`を固定して追加した。OpenCV公式のnpmパッケージではなく、[TechStarkによる配布](https://github.com/TechStark/opencv-js)である。配布JSをViteのアセットとして同じオリジンから取り込み時だけ読み込み、Classic Workerの中で処理する。非圧縮の配布JSは約10.9MB。Matはfinallyで破棄し、成功・失敗・中止・タイムアウトでWorkerも終了する。

この版の`cv`は自身を返すthenableなので、`await cv`では初期化待ちが循環した。初期化コールバックから値を返さず完了だけを待つ方法に修正し、4画像での実行を確認した。

初期版の処理は、外周につながる黒背景の除去、中性色の選別、二値化、細かいノイズの除去、直線検出、平行線の統合の順だった。標準感度と細線を残す感度を選ぶUIは、後述の改善で撤去した。検出線から床の正しい領域や建具の意味を推論したとは扱わない。

単体テストは多角形の自己交差、開口部の重なり・範囲、寸法補正、線の統合、不正な解析結果、個人保存の版と共有ガードを対象とする。ブラウザテストでは実際のOpenCV配布とWorkerを使い、3D部分だけを置換するUIテストと、実WebGLのテストを分けている。初期OpenCV版のローカル実行でユニット123件、通常のE2E全50件（UI40件・実WebGL10件）、本番ビルドが成功した。開発サーバーでも白黒図面の解析・適用・第2版の保存を確認した（この確認では3Dモジュールを置換し、実WebGLは前述のE2Eで確認）。GitHub Actions上の実行と実バックエンドとの結合は未確認。

画像の外部アップロード・AIモデルの実行は行っていない。

## 精度と感度選択UIの再調査（2026-11-06）

利用者から認識精度と感度選択への指摘を受け、実装と一次資料を再確認した。この節は再調査時点の改善案を記録しており、後段の改善実験で一部を実装した。再調査自体ではコード・UI・依存を変更せず、追加モデルの実行や画像の外部送信も行っていない。

### 現在の処理で精度を落としている点

`opencv-worker.js` は固定の明るさ閾値175、中性色の差45、1×1または2×2のカーネル、画像の長辺に対する一定割合の最短線長、固定5pxの結合距離で処理している。

- 壁の領域や用途を認識せず、暗い長い線分を壁候補として扱う。文字・タイル・浴槽・家具も同じ条件で通る。
- 2×2のノイズ除去で1px程度の細線を失う場合があり、最短線長によって短い間仕切りも落とす。細線を残す設定では、同時に不要な線も増える。
- 塗りつぶされた太い壁から複数の平行線を検出する。`floor-plan-detection.js` の固定的な近接統合だけでは、壁の中心線や本来の厚みを安定して復元できない。
- 壁の交点・接続関係、閉じた床領域、開口部との整合を評価していない。個別の線が正しくても、間取り全体が正しいとは限らない。
- 床は常に仮の長方形、開口部は空配列を生成する。ここは感度を変更しても自動化されない。

前回のユニット・E2Eは計算の制約、操作、保存、実WebGL表示の検証である。正解の壁・床・開口部との照合ではなく、全件成功を認識精度の検証として扱わない。

### 感度を選ばせない方法

利用者の標準フローは「画像を選ぶ → 自動解析 → 要確認箇所を修正 → 実寸を指定 → 3Dに適用」とする案を推奨する。標準／細い線という画像処理上の設定は画面から外し、利用者の操作は「この候補を壁として残す／削除する」「不足する壁を追加する」「この長さは何mか」のように対象物に結び付ける。

内部では次の候補を比較する。

1. 固定の二値化だけにせず、画像の分布から閾値を決めるOtsu法や、局所的な明るさへ対応する適応的二値化を試す。[OpenCV公式説明](https://docs.opencv.org/4.x/d7/d4d/tutorial_py_thresholding.html)
2. 壁らしい太さの分布を推定し、画像解像度に応じてノイズ除去・最短線長・統合距離を決める。距離変換は太さ推定の材料になり得るが、文字の太い画もあるため単独では分類に使わない。[距離変換の公式API](https://docs.opencv.org/4.x/d7/d1b/group__imgproc__misc.html)
3. 壁領域から中心線・端点・交点を作り、近接した端点の接続、重複の除去、短い枝や孤立候補の確認を行う。短い壁を一律に捨てたり、開口部をすべて塞いで閉領域を作ったりしない。
4. 内部で複数の前処理候補を試す場合は、元画像の線への支持、厚みの一貫性、重複、接続、開口部の証拠を評価して選ぶ。単に線の本数が多い／少ない、閉領域が多いという基準にはしない。自動選択の評価式自体にも正解データによる検証が必要。
5. 不確かな候補を一律に3D化せず、画像上で確認できる表示にする。候補の確からしさを示す場合は、未校正の指標を「正解確率」と表示しない。

Otsu法などは画素の分離を改善する手段であり、家具や文字を壁と区別する専用認識ではない。感度UIの撤去と認識精度の改善は別の課題として評価する。

フロントのみという条件では、モデルをONNXへ変換し[ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/)のWASMまたはWebGPUで動かす方法が候補になる。ただし、変換後の精度、演算の対応、モデル配布容量、ピークメモリ、対象端末の速度を確認する必要がある。「ONNXのPython推論がある」ことと「ブラウザで実用になる」ことを混同しない。

外部のVLMで画像からJSONを得る案もあるが、細かな座標・接続の誤りを形状検証で検出する必要があり、見た目が自然でも正しい復元とは限らない。APIキーの秘匿と画像送信を伴う構成は、現在の端末内処理とは別の仕様になる。本調査では採用を決定していない。

### 推奨する比較と実装順

1. 提供4画像に壁の正解形状と開口部・床輪郭の注釈を付け、現在の出力を基準として記録する。開口部の認識をまだ実装していないことも区別する。
2. 感度選択を外すことをUXの方針とし、内部の自動前処理＋接続関係の補正を実験する。追加の設定を利用者に増やさない。
3. 利用条件を確認できた専用モデルを同じ4画像で並行比較する。精度を優先する場合はこちらが本命の調査対象で、閾値調整だけを際限なく続けない。
4. 壁の誤検出・欠落、中心線の位置、交点の接続、開口部の壁への割り当て、床の重なり率、利用者の修正操作数と所要時間を比較する。画素のIoUだけで採否を決めない。
5. 4画像への過剰な最適化を避け、別の図面を保持して評価する。処理時間・ダウンロード量・メモリもモバイル相当で測る。

現時点の結論は「感度は内部で自動化し、意味を区別する認識と形状の整合性を強化する」。どの候補が何％改善するかは未測定である。今回はフロントだけで可能な改善案を優先しており、新たなバックエンドAPIが必要な採用方針までは決めていない。

## AIを使わない自動解析の改善実験

利用者の指定に合わせ、OpenCV.jsとブラウザ内の処理だけで試した。感度の選択欄を撤去し、画像から内部設定を決める。モデル・外部API・新しい画像処理依存は追加していない。

### 採用した処理

- 黒い外側背景と中性色でない塗りを除き、局所的な二値化を行う。近傍サイズは画像解像度に合わせて決める。
- 水平・垂直方向の長い帯をモルフォロジー処理で取り出し、帯の中央を壁の中心線にする。太い壁の内部から多数の線を作る方式を主経路にしない。
- 長い帯の太さから画像内の代表的な線幅を推定し、細線の除外・救済と統合距離を決める。画像全体が細い線の場合は、それを一律に消さない。
- 規則的に並ぶ薄い線をタイル状の模様として抑える。細線は壁への接続を根拠に救済し、玄関突出部・バルコニー・デッキのような外側へ延びる枠も候補にできる。
- 壁同士が近いだけではつながない。元の二値画像上でも接続が確認できる交点だけを補正する。平行な線の統合で離れた線分の隙間を一律に埋めない。
- 斜線は長さと帯の太さの裏付けを確認して残す。扉の弧の接線などの混入を抑えるが、斜めの壁全般を検証できたわけではない。

床は引き続き仮の長方形で、開口部・バルコニーの種類を自動判別する処理はない。物件掲載図面では、収納の区切りと家具・設備の線の区別も一部残る。

### 評価方法

`e2e/fixtures/floor-plans/references.json`に、目視で選んだ壁・外枠の中心線と、文字・浴槽・家具・玄関タイルなどの非壁領域を記録した。図面全体の正解注釈ではなく、今回の4画像を見ながら選んだ開発用の部分注釈である。独立した評価セットや一般的な認識精度として扱わない。

- **選んだ壁の網羅率**: 各参照線を約1px間隔でサンプリングし、向きが一致する候補線が4px以内にある割合を求め、参照線ごとに平均する。全壁の再現率や全体の画素IoUではない。
- **指定した非壁領域内の線長**: 候補線のうち、注釈した非壁領域内に入った長さをpxで求める。0pxでも、その領域外での誤検出がないとはいえない。

従来版は固定閾値175・2×2カーネル・HoughLinesPによる出力を`baseline-lines.json`へ画像座標で保存した。同じ注釈・評価関数で比較する。比較を再実行するコマンドは次のとおり。

```bash
npm run test:floor-plan --prefix frontend
```

PlaywrightでJPEGをデコードし、製品のWorkerと同じソースをNode.jsのOpenCV上で実行する。Nodeの比較だけでブラウザのWorkerを確認したとは扱わず、通常E2Eで別途検証する。通常E2Eと共通の実行ロック・ブラウザ起動前確認を使用し、出力は`frontend/test-results/floor-plan-evaluation.json`。CIもE2E後に比較コマンドを実行し、同じ成果物として保存する。

### 不採用・比較した案

- **大津法＋帯抽出だけ**: 選んだ壁は拾いやすくなったが、白黒図面の浴槽や着色図面のタイルの混入が増えた。指定した非壁領域内の候補線長は白黒122px・着色646.3pxとなり、単独では不採用。
- **近い線なら細線を救済**: タイルや家具の枠も壁へつなぎ直したため不採用。画素の接続確認と繰り返し模様の抑制を追加した。
- **大津法＋接続制約**: 誤検出は減ったが、局所二値化のほうが着色・木目図面の選んだ壁を拾えた。大津法を主処理には採用しなかった。
- **離れた平行線も5pxまで結合**: 短い開口を埋める可能性があるため撤去。壁の向きを揃えた後の長さを再計算し、線幅に応じて重複のみを統合する。

Node.js上での4画像の処理は従来約140〜238ms、改善版約260〜546msだったが、これはCodespacesの単回の実験で、画像のデコード・ダウンロード・ブラウザWorkerの起動を含まない。初回のWASM初期化を含む比較コマンドの値や、E2E全体の時間と混同しない。速度を改善したとは判断していない。

## 扉と出っ張りの補正

`images (1).jpg`の確認を受け、帯全体の包囲矩形を一枚の壁にする処理を改めた。断面の太さ・位置が変わる区間を分け、太い壁をつなぐ扉の細線を壁へ戻さない。短い折れ返しは両端が別方向の壁へ接続し、画素の裏付けがある場合に拾う。近接する平行な輪郭は両端のキャップが確認できる場合だけ厚い壁へまとめる。キャップの照合は端点から内側3pxまでとし、白い隙間を距離だけで埋めない。

画像上の局所厚さを`thicknessRatio`として実寸モデルへ渡す。省略時1、有限数0.1〜8で、実厚さは基準厚さとの積。保存・復元・全体寸法変更・立体化で維持し、編集画面の「この壁の厚さ (m)」でも調整できる。既存保存データは自動再解析しないため、改善を反映するには元画像を取り込み直して適用する。

以前の部分注釈には閉じた扉の線も正例として含まれていた。元画像を拡大して照合し、着色図面のトイレ・浴室・玄関・ホール入口、木目図面の収納扉を正例から除いた。木目図面の寝室入口は壁の縦線ではなく、その左側の通路であることも確認した。閾値を下げて合格させず、実際の入口を負例として追加した。過去表の値と現在の値は注釈が異なるため、そのまま改善率として比較しない。

追加評価は生成した壁ボックスの床上0.5mに対する包含判定で、入口の遮蔽・出っ張り内部の欠落・外部の不要な壁を数える。着色図面の6入口とキッチン横の出っ張り内外を対象とする。点の検査であり、開口全体の形状・建具の種類・すべての壁の正しさの保証ではない。通常UI E2Eと実WebGL E2Eも同じ形状検査を行う。

細線を一律に強い壁へ昇格する案は浴槽などの混入が増えるため不採用。外枠の救済は強い壁の外側に限定し、接続経路の近傍に線画素があることを確認する。薄い壁・家具との区別や床輪郭は引き続き手動修正が必要。


補正後の部分注釈で、保存した従来線データと現実装を同じ関数で比較した結果は次のとおり。

| 画像 | 部分壁の網羅率: 従来線データ → 補正後 | 非壁領域内の線長: 従来 → 補正後 |
| --- | --- | --- |
| 白黒 | 74.9% → 99.7% | 0.0 → 0.0px |
| 着色 | 58.8% → 95.8% | 320.3 → 0.0px |
| 黒背景 | 66.5% → 76.3% | 289.1 → 0.0px |
| 木目 | 85.4% → 91.2% | 79.0 → 0.0px |

選択した入口の遮蔽点、出っ張り内部の欠落点、輪郭外の壁点はすべて0。白黒・黒背景にはこの追加点注釈がなく、0はその画像の開口を検証したことを意味しない。これらは同じ4枚を使って調整した開発用の部分評価である。

補正後のローカル検証ではユニット138件、通常E2E50件（UI40件・実WebGL10件）、本番ビルドが成功した。通常E2Eの計測はビルド18.7秒・テスト321.5秒で、単回の実行結果。GitHub Actions上では未確認。
