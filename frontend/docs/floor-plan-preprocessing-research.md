# 間取り図の前処理に関する追加調査

本書は実装前の調査記録です。後続の全6枚・9方式の結果と採用条件は[前処理実験](floor-plan-preprocessing-experiments.md)を参照してください。

調査日: 2026-11-09。基準実装: `b49d9cd` / Issue #28。対象はAIを使わず、ブラウザ内で完結させる前処理。[前回の改善実験](floor-plan-improvement-experiments.md)の後続調査である。

## 結論

**前処理は追加検証する価値がある。ただしフィルターを一律に足すより、入力の正規化と、色・細線を失わない条件の検証を先に行う。** 今回、透明背景の扱いと現行の色救済の相互作用、メディアン処理による細線消失を小さな診断で確認した。

次の優先順位が妥当と判断する。効果が実測済みのものと、試すべき仮説を区別する。

| 優先 | 対象 | 期待する効果・根拠 | 注意点・現在の確認範囲 |
| --- | --- | --- | --- |
| 最優先 | 透明背景の正規化と色救済条件の併用 | 透明RGBが黒い外側背景の判定に混ざる実害を再現 | 白背景合成だけでは色付き壁の認識が悪化する実画像も再現。単独採用しない |
| 高 | 弱いエッジ保持平滑化 | JPEG由来の小さい濃度変動を抑えつつ境界を残す候補 | `bilateralFilter`を第一候補に比較。実図面の認識改善は未測定 |
| 高 | 二値化方式の比較（Sauvola等） | 局所平均だけでなく分散も使い、背景ムラへの対処を試す | 木目・文字・家具も強調され得る。壁を意味で分類する処理ではない |
| 中 | 背景の明るさの平坦化・弱いCLAHE | 影や薄い印刷のコントラストを補う候補 | 木目・タイル・JPEGノイズの増幅に注意。全画像への一律適用はしない |
| 条件付き | 傾き補正 | 現行の水平・垂直の帯抽出に対し、傾きによる分断を減らす候補 | 多数の長線の向きが一致するときだけ。既存図面が概ね整列している場合の効果は限定的と推測 |
| 条件付き | 余白・縮小方式の比較 | 縮小で弱くなる細線を可能な限り残す | 元から低解像度の画像の情報は復元できない。既存4枚は長辺1024px以下 |
| 後段 | 文字候補・規則的な模様の分離 | 非壁の線を壁抽出用マスクから抑える候補 | 小さい物体の一律削除では短辺・細い壁も消える。家具の意味分類の代わりにはならない |

製品の認識処理は今回変更していない。全6図面の前処理比較や採用判断は、次の実験で行う。

## 現在の前処理と不足

`floor-plan-image.js`は画像を長辺1024pxへ縮小し、CanvasからRGBAを取得する。Canvasを白で塗ってから描画する処理や、縮小方式の比較はない。

`opencv-worker.js`では、RGBが暗い画素の端からの連結で外側背景を除去し、グレースケール化、有彩色の除外、局所Gaussian二値化を行う。その後、水平・垂直の帯抽出、線幅推定、細線救済・開口保持等へ進む。通常結果が0本の場合だけ有彩色の除外を外して再解析する。

未実施なのは、傾き補正・ノイズ除去・明るさ補正・別の二値化などを独立させ、認識器を固定して全6枚で比較する実験である。前回の線幅・端点補正は主に候補抽出後の処理で、この比較の代わりにはならない。

また、後段には画像サイズの約3.5%の最小線長、推定線幅に対する支持判定等がある。前処理で残った線も後段で落ちる可能性があるため、最終候補数だけで前処理の成否を判断しない。

## 今回確認した問題

### 1. 透明な背景で黒い壁が外側背景と一緒に消える

初期の外側背景判定は `max(R,G,B) < 40` で、アルファを考慮しない。透明な画素のRGBが0なら黒い背景として端から探索され、そこに接する不透明な黒い壁も同じ連結領域として除外され得る。後から透明画素を白へ置き換えても、この外側判定を取り消せない。

同じ黒い長方形の枠を200×200pxに描いた合成入力で、製品Workerと同じコードをNode.js上のOpenCVで実行した。

| 背景 | 不透明な黒い壁 | 検出後の実寸モデルの壁数 |
| --- | --- | ---: |
| 白・不透明 | 同じ4辺 | 4 |
| 透明・RGB=0 | 同じ4辺 | 0 |

これは透明入力に関する不具合の再現であり、全6図面の改善率ではない。次はブラウザの実Canvas・Workerでも同じ見え方のPNGを使って確認する。

候補は外側背景判定より前に白背景へ正しくアルファ合成する方法、または外側の暗色判定に不透明度を含める方法。部分透明の縁も単に切り捨てず、合成後の画素を評価する。Tesseractの公式資料にも白背景へのアルファ合成の例があるが、OCRでの記述を間取り認識の性能保証として扱わない。[Tesseractの前処理・アルファの説明](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html#transparency--alpha-channel)

### 2. 白背景合成だけでは、現行の色救済を無効にする場合がある

追加の色付き住宅図面 `holdout/cottage.png` をPillowでRGBAへ展開し、そのままと白背景合成後の2通りを同じWorkerコードへ入力した。解像度は848×903のまま。モデル変換と監査済み部分注釈も同じにした。

| 入力 | 色を残す再解析 | 壁数 | 選択した壁の網羅率 |
| --- | --- | ---: | ---: |
| 元のRGBA | 実行する | 30 | 88.95% |
| 白背景に合成したRGBA | 実行しない | 7 | 0.00% |

白背景化で以前は消えていた別の線が残るため、通常解析の候補が0本ではなくなり、色付きの主要な壁を救済する再解析が作動しない。単純に前処理を足すと、この図面では悪化することを確認した。

この診断はNode.js上での単画像比較で、実ブラウザの新たな全6枚比較ではない。PillowとCanvasの部分透明・色管理の差も未検証。前回の「通常結果は変えない」という救済条件は、その前段の処理を変えた場合まで不変を保証しない。

今後の候補は、中性色と有彩色の候補を別々に評価し、長い帯・接続・原画像の支持を根拠に補完する方法。候補が少ないという理由だけで有彩色へ切り替えるのも、文字や家具を増やす危険がある。この併用は未実装・未検証。

### 3. 3×3メディアンでも1pxの壁を消せる

200×200pxの白背景に、濃度160・太さ1pxの長方形の枠を描いた合成入力を比較した。

| 処理 | 検出後の実寸モデルの壁数 |
| --- | ---: |
| 前処理追加なし | 4 |
| グレースケールに3×3メディアンを適用 | 0 |

メディアンが周囲の白い画素を優先するため、細い壁まで消える。したがってノイズ除去の基準は見た目の滑らかさではなく、細線・短辺・開口を保持できるかで決める。

OpenCV公式資料ではメディアンは主に塩胡椒ノイズに有効で、bilateralは境界を保ちながら平滑化する一方、計算コストが高いと説明されている。JPEGノイズと塩胡椒ノイズを同一視せず、弱いbilateral・処理なし・小さいメディアンを別案として比較する。bilateralでも細線保持を保証するわけではない。[OpenCV 4.12のフィルター説明](https://docs.opencv.org/4.12.0/d4/d13/tutorial_py_filtering.html)

## 一次資料から得た候補

### Sauvolaによる二値化

局所平均と標準偏差に応じて閾値を決める文書画像向けの手法。現在の局所Gaussian二値化と差があるため、薄い印刷・背景ムラへの候補として比較する。原論文はSauvola / Pietikäinenの2000年の論文。scikit-imageの公式例にも局所統計と比較コードがある。[公式例と原論文参照](https://scikit-image.org/docs/stable/auto_examples/segmentation/plot_niblack_sauvola.html)

現行配布のOpenCV.jsには `niBlackThreshold` / `ximgproc` の公開APIがなかった。C++版にはSauvola対応があるが、その呼び出しをそのままJSへ移せない。局所平均・二乗平均から分散を計算する実装が候補で、境界処理、メモリ、速度、出力の一致の検証が必要。手法が文書画像向けであることだけで今回の間取りへの優位性を主張しない。[OpenCV 4.12 ximgproc](https://docs.opencv.org/4.12.0/df/d2d/group__ximgproc.html)

### CLAHE・背景補正

局所的なコントラストを補う候補。OpenCV公式資料は、通常の局所ヒストグラム平坦化がノイズも増幅し、CLAHEは増幅を制限する設計であることを説明している。木目のような模様が壁らしくなる場合があるため、既にコントラストの高い図面に一律適用しない。[OpenCV 4.12 CLAHE](https://docs.opencv.org/4.12.0/d5/daf/tutorial_py_histogram_equalization.html)

背景のゆっくりした明るさの変動を推定して補正する方法も候補だが、推定の窓が壁の太さに近いと壁まで背景として消し得る。背景推定前後の画像と壁支持マスクの両方を保存して比較する。今回、実画像での有効性は測っていない。

### 傾き補正

Hough等で長い線の方向を集め、その向きが水平・垂直から同じ角度だけずれている場合に限定して補正する案。扉の弧・家具・本来の斜め壁で角度を決めないよう、多数の長線の一致を必要とする。現在は軸方向の長い帯を重視するため、傾いた細線が途切れる可能性があるという実装上の推測に基づく。[Houghの公式例](https://scikit-image.org/docs/stable/auto_examples/edges/plot_line_hough_transform.html)、[OpenCVの方向別モルフォロジー](https://docs.opencv.org/4.12.0/dd/dd7/tutorial_morph_lines_detection.html)

画像を回転させる場合は白い余白を確保して端を切らず、原画像と解析画像の座標変換を保持する。重ね合わせ、壁の手動追加、2点による寸法校正、評価注釈も同じ座標系へ対応させる。補正角だけを認識器に渡し、プレビューや注釈を元の座標のまま使わない。

### 縮小・解像度

OpenCVは縮小用の補間として `INTER_AREA` を案内している。Canvasによる縮小との比較候補だが、面積平均で薄い線のコントラストが下がる場合もあり、必ず壁認識が上がるとはいえない。[OpenCV 4.12 resize](https://docs.opencv.org/4.12.0/da/d54/group__imgproc__transform.html)

既存4枚はいずれも長辺1024px以下で、現在の取り込みでは縮小されない。したがって縮小方式を変えるだけで既存4枚の問題を解決できるとは考えない。大きい歴史的図面などで、余白整理・縮小方式・必要なら複数解像度を比較する。

現状の `floorPlanFromLines` は画像座標の各辺を32〜1024pxで検証する。1536pxや2048pxの解析を試す場合は、この契約と縮小・座標変換・Matのメモリ使用を一緒に見直す必要がある。上限だけ変えて同じ処理が実用的に動くとは判断しない。

### 文字・家具・模様の扱い

連結成分・MSER・規則的な間隔・線幅を使う古典的な候補分離は可能だが、細い壁や短い折れ返しも似た特徴を持つ。文字候補を塗り潰したりinpaintingしたりすると、接触する壁や開口を誤って変える危険がある。

まず元画像を消去せず、壁検出用の候補マスクを分ける。長い壁や交点につながる部分を保護し、最終接続の支持は正規化後の元画像でも確認する案がよい。これは設計上の提案であり、今回の6図面で有効と実証した処理ではない。Tesseractは前処理の資料として参照しただけで、OCRや学習済み文字モデルを採用する提案ではない。

`@techstark/opencv-js` **4.12.0-release.1**を初期化して、Node.js上で公開APIを確認した。Python版のAPI名をそのまま使えると仮定していない。

| API | 確認結果 |
| --- | --- |
| `medianBlur`, `GaussianBlur`, `bilateralFilter` | 関数あり。メディアンの合成入力比較も実行 |
| `CLAHE` | クラスあり。`new cv.CLAHE(2, new cv.Size(8,8))` と32×32の `apply` を実行 |
| `createCLAHE` | 公開されていない |
| `integral`, `boxFilter`, `sqrBoxFilter` | 関数あり。Sauvola実装の候補となるが未実装 |
| `warpAffine`, `HoughLinesP`, `resize` | 関数あり。前処理としての品質・座標復元は未検証 |
| `connectedComponentsWithStats` | 関数あり。前回の床推定実験でも使用 |
| `MSER` | コンストラクターと `detectRegions` があることを確認。文字領域の検出品質は未検証 |
| `MSER_create`, `niBlackThreshold`, `ximgproc` | 公開されていない |

このAPI確認と合成診断だけで、ブラウザWorkerの前処理パイプラインの検証完了とはしない。

## 次の比較の進め方

1. **基準を固定する。** 現在の製品コードと6入力・注釈を固定し、後段の線幅・端点・床の処理は変えない。前処理による変化だけを測る。
2. **入力正規化と色救済の組合せを先に比較する。** 白背景合成だけで悪化するCottageも含め、原版・アルファを考慮した外側判定・白背景合成と色候補併用を切り分ける。合成入力では透明・不透明の見え方が同じ画像の結果一致を確認する。
3. **一度に1系統を追加する。** 弱いbilateral、Sauvola、弱いCLAHEをそれぞれ単独で比較する。傾き補正は原版6枚と、既知角度で回転させた検証用画像でも確認する。合成ノイズを加える場合も原版の評価と分ける。
4. **最終結果だけでなく中間画像を残す。** 元画像、正規化後、平滑化後、二値化、壁支持、認識重ね合わせ、3Dを保存する。二値化では残った壁が後段で消えたのか、前処理で消えたのかを区別する。
5. **判定は画像ごとに行う。** 部分壁の網羅率だけでなく、開口の遮蔽、非壁の混入、短辺・1px線の保持、床、保存・復元、処理時間・メモリを見る。平均値の上昇で特定の図面の悪化を隠さない。

基準の6枚を繰り返し見て調整しているため、独立した評価セットではない。前処理で家具と壁の意味の区別が解決する、どの方法で何%改善する、という結論はまだ出せない。
