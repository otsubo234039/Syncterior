# Frontend

React / Vite / React Three Fiberで実装した家具配置シミュレーターです。

```bash
npm install
npm run dev
npm run build
npm run preview
npm test
```

## 開発ページを開く

`npm run dev` は `0.0.0.0:5173` で待ち受けます。ローカルでは `http://localhost:5173/` を開き、Codespacesでは「ポート」タブの5173番をPrivateのまま「ブラウザーで開く」から表示します。5173番が使用中なら起動を止め、別のポートへ自動変更しません。Codespacesの転送ホストは`CODESPACE_NAME`と`GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN`から組み立てて許可します。設定変更前から起動していたサーバーは停止して起動し直してください。

「ページが見つからない」「接続できない」場合は、端末に起動完了が表示されていること、開いている転送URLのポートが5173番であることを確認します。開発ページは`frontend/`のViteが提供します。バックエンドは未実装で、E2E専用APIの4175番を開いてもアプリは表示されません。`npm run preview`は4173番固定でビルド結果を提供し、使用中ならエラーで停止します。

### 起動済みなのにページを開けない場合

- `Port 5173 is already in use` は、そのポートを別の開発サーバーが使用していることを示します。既存サーバーが正常なら追加起動は不要です。再起動するときは、起動元のターミナルでCtrl+Cを押してから起動します。
- Codespacesでは「ポート」タブの5173番から開きます。PrivateポートはCodespaceにアクセスできるGitHubアカウントでの認証が必要です。
- 「Codespaces Access Port」「You are about to access a development port...」というGitHubの確認画面が表示されたら、自分のCodespaceのURLであることを確認して「Continue」を押します。この確認画面のHTTP 200は、アプリ画面の表示成功とは別です。
- 接続の確認では、localhostの応答に加え、実際の転送URLで認証・確認画面を通った先にROOMが表示されることを確認します。表示されない場合は、開いているURLとエラー文を切り分けて調べます。

参考: [GitHub公式のポート転送手順](https://docs.github.com/en/codespaces/developing-in-a-codespace/forwarding-ports-in-your-codespace)。

内部では表示できるのに転送URLが404になる場合の類似事例・更新情報・切り分けは[Codespaces転送の調査](docs/codespaces-port-forwarding-investigation.md)を参照してください。認証だけを原因と決めず、Privateのまま転送登録の停止・再追加も確認します。

## 構成

Bulletproof Reactの考え方に沿って、機能単位にコードをまとめています。

```text
src/
├── main.jsx                     # Reactの起動
├── app/
│   ├── app.jsx                  # アプリ全体の構成
│   └── styles.css               # 全体のスタイル
├── components/
│   └── layout/app-layout.jsx    # 共通ヘッダー・フッター
└── features/
    └── room-planner/
        ├── index.js             # 機能外に公開する入口
        ├── api/                 # 共同編集API・SSEへの接続
        ├── components/          # 画面UI・3D描画
        ├── hooks/               # 家具配置の状態管理と操作
        ├── data/                # 間取り・家具カタログの定義
        └── utils/               # 配置計算・検証・ブラウザ内保存
```

## 依存関係と追加方法

- `app`は共通レイアウトと各機能を組み合わせます。機能の利用は`features/<機能名>/index.js`を経由します。
- `features`内のコードは同じ機能内のモジュールや共通コードを参照します。他の機能の内部ファイルは直接参照しません。
- `components`には機能に依存しない共通UIを配置します。`app`や`features`は参照しません。
- 家具配置の状態と操作は`useRoomPlanner`に集約し、UI・3Dコンポーネントにはpropsで渡します。
- 家具を追加する場合は`data/catalog.js`、`planner-sidebar.jsx`のアイコン対応表、`furniture.jsx`の形状を更新します。間取りは`data/plans.js`に追加します。
- 共通化が必要になった時点で共通モジュールを追加します。未使用の層やディレクトリは用意しません。

現在はJavaScriptのまま構成を整理しています。ディレクトリ間の依存ルールは運用上の規約で、Lintによる強制は行っていません。

## 図面モード（Issue #19 / #50）

個人編集の初期画面は「図面モード」です。2D図面を設計データとして作成・保存し、「図面から3Dを表示」で同じ実寸の形状を立体表示します。図面だけの編集・保存では3Dモジュールを読み込みません。共有リンクは従来の「3D・家具配置」を開き、図面モードは利用できません。

1. 初期の8m×6mの床に作図するか、「図面の新規作成・読込・画像変換」→「新しい図面を作成」で図面名・幅・奥行き・高さを指定します。
2. グリッドを目安に「壁を追加」で2点を指定し、「線を消す」で不要な壁を1本単位で削除します。床・開口・端点も編集できます。
3. 「図面情報」で名前・壁の高さを変更できます。「図面情報を更新」で編集へ反映するほか、保存・3D表示時にも入力を反映します。既存の開口が収まらない高さは拒否します。
4. 「図面を保存」で、このブラウザに1つの図面を保存します。3Dを開く必要はありません。未保存の変更はモード切替で維持し、新規作成・読込・画像変換による置換時は確認します。変更後のページ離脱にもブラウザ標準の確認を要求します。
5. 「保存した図面を開く」で最後の保存へ戻せます。「図面ファイルを書き出す」「図面ファイルを開く」でJSONを持ち出せます。ファイルは1MB以下で、版・形状を検証します。複数案の一覧管理や家具を含むファイル出力は未対応です。
6. 「図面から3Dを表示」で図面の形状を「3D・家具配置」へ反映します。図面保存とは独立しており、この操作は図面の保存を代行しません。同じ図面の修正では家具の位置・寸法を維持し、収まらない反映を拒否します。新規作成・別画像の変換・別図面の読込では、前の家具を引き継がず家具なしの間取りを生成します。取り込みと保存だけでは前の3D配置を変更せず、3D表示時に置き換えます。

図面の保存は `syncterior.drawing` の `{version:1, plan, drawingId?}` 形式です。`plan` は `floor-plan.js` の壁・床・開口・高さを持つメートル単位モデルで、JSONファイルも同じ形式です。PNGやSVGの画像ではありません。元画像、表示倍率、グリッド設定、編集履歴、生成メッシュ、家具は含めません。3Dの家具配置は従来の `syncterior.personal-room`（プリセット第1版／custom第2版）で別に保存し、customの保存エンベロープに元図面の`drawingId`を任意で持たせます。図面形状とAPIのroomにはIDを混ぜません。図面の保存・読込だけでは上書きしません。

図面の保存がなければ従来の個人配置のcustom形状を編集の初期値として開きます。この読み込みだけでは新しい保存キーへ書き込みません。破損した図面や保存領域の拒否は案内し、編集を継続できます。保存失敗時にはJSONファイルで持ち出せます。保存はブラウザ内のみで、サーバーの図面管理・共有は未実装です。形状共有はBE-11 / #43を参照してください。

## 間取り画像を図面へ変換（Issue #28）

「図面の新規作成・読込・画像変換」→「間取り画像を図面へ変換」でJPEG・PNG・WebP（10MB以下、各辺32〜8192px、合計2000万画素以下）を選びます。長辺1024px以下に縮小し、OpenCV.jsを取り込み時だけ読み込んでWorker内で解析します。画像はサーバーへ送りません。追加の起動コマンドや外部APIキーは不要です。

画像上の青い壁候補と仮の長方形床を確認します。感度の指定は不要で、解析は中止・再実行できます。認識結果を正解とせず、壁・扉・窓・床を確認してください。

実測値で補正するには、一辺の両端を図面上で指定し「測った一辺の長さ (m)」を入力して「この長さで全体を補正」を押します。形状・壁厚・開口幅を一様に補正し、高さは維持します。認識された壁の区切りや部屋境界に合わせる必要はありません。計測点はドラッグ・矢印キーで微調整でき、補正は取り消せます。同じ値の再適用で二重に拡大しません。交点への吸着・自動室認識・畳数補正は未対応です。

「図面へ変換」で編集可能な図面へ反映し、元画像を下絵にします。変換や実寸補正だけでは図面保存・3D配置・個人配置保存を変更しません。図面モードで手直しして「図面を保存」し、必要なときに「図面から3Dを表示」を押します。元のサイズは約8mを仮定した概算で、一辺からの補正は縦横比の正しい画像が前提です。

数値中心の壁・床・開口編集フォームや1/n表示は取り込みに設けません。新規作図・詳細な形状編集は図面モードに集約します。3D化したcustom間取りでも家具を追加・移動・回転・色変更・削除し、個人保存できます。共有は#43対応まで無効です。

OpenCV.jsは`@techstark/opencv-js@4.12.0-release.1`を固定して使用し、配布JSは約10.9MB（非圧縮）です。ライセンスは `public/licenses/opencv-js-Apache-2.0.txt` に同梱しています。認識エンジンはOpenCV、図面への変換と3D化は本アプリの処理です。

### 解析改善の比較

`npm run test:floor-plan`で4画像の現在の解析と保存した従来の線データを比較し、`test-results/floor-plan-evaluation.json`へ結果を出力します。Playwrightのブラウザが必要で、起動前確認と通常E2Eと共通の実行ロックを使います。参照は`e2e/fixtures/floor-plans/references.json`の人手で選んだ一部の壁・非壁領域であり、図面全体の正解ではありません。誤差4px以内で対応する壁の網羅率と、指定した文字・家具・タイル領域内の候補線長を別々に測ります。

通常のE2Eでも、感度選択がないことと部分注釈に対する欠落・誤検出の上限をデスクトップ・モバイルで確認します。CIはE2E後に比較コマンドも実行して結果を成果物へ含めます。比較コマンドのOpenCV処理はNode.jsで実行し、ブラウザのWorker・3D表示はE2Eで別に確認します。実験と残る制約は[調査記録](docs/floor-plan-import-research.md)を参照してください。

## 家具移動中の視点固定

家具を左ボタンまたはタッチで押している間、`useFurnitureDrag`がOrbitControlsを無効にします。ボタンを離す・操作をキャンセルする・ウィンドウがフォーカスを失う・家具がアンマウントされると、元の視点操作の状態に戻ります。家具以外の場所では従来どおり視点を操作できます。

移動先はドラッグ開始時の高さに固定した水平面とポインターのレイの交点から計算し、つかんだ位置と家具の中心とのオフセットを保持します。壁や他の家具の表面座標に切り替わって家具が飛ぶのを防ぎます。

ドラッグの開始・終了、中断時の復帰、表面座標が切り替わった際の移動先の安定性は、`utils/__tests__/furniture-drag.test.js`で検証しています。追加のテスト用依存関係は不要です。

## 個人配置の自動保存（Issue #18）

個人編集の間取り・家具ID・位置・回転・寸法・色は、操作時にこのブラウザのlocalStorageへ自動保存し、個人用ページを再読み込みしたときに復元します。選択中の家具・カメラ・共有部屋ID・revision・未確定操作は保存しません。初期表示だけでは書き込まず、保存結果と読み込み・書き込み・消去の失敗を画面に表示します。保存に失敗しても画面内の編集は継続できます。

保存キーは`syncterior.personal-room`、形式は`{ "version": 1, "room": { "planKey": "studio", "items": [...] } }`です。版・間取り・家具の件数とID・数値・色・回転後の境界を検証し、破損・未知の版・不正な配置は復元せず、初期配置で表示します。不正な保存内容も勝手に消去せず、次の個人編集または明示的な消去まで保持します。検証と読み書きは`utils/local-room-storage.js`、個人操作の通知は`room-session.js`で扱います。

「保存した個人配置を消去」はこのキーだけを削除し、現在の画面の配置は維持します。そのまま再読み込みすると初期配置になり、次に個人編集を行うと再び保存します。共有リンクでは個人保存を読み込まず、共有の取得・同期・再接続・退出だけでは個人保存を変更しません。退出後は従来どおり最後に確定した共有配置を表示し、その状態で個人編集したときに初めて保存を更新します。

同じオリジンの同じブラウザ内での保存です。別タブで最後に編集した内容が保存されますが、開いている他タブへの自動反映は行いません。端末間同期やサーバーの永続保存は引き続き未実装です。

## 回転後の家具と部屋の境界（Issue #13）

移動・数値入力・90度回転では、回転後のXZ平面上の外形を使って部屋の範囲に収めます。壁際での回転は、はみ出す軸だけ最寄りの位置へ補正します。中央へのリセットは行いません。寸法そのものは変更せず、回転後の外形が部屋より大きい場合や数値が不正な場合は、元の向き・位置を維持します。家具同士の衝突回避は対象外です。

境界計算は`utils/furniture-bounds.js`、操作への適用は`room-state.js`にあります。ユニットテストは四隅を独立に検証し、UIでは各方向の数値入力・壁際の回転、実WebGLでは回転した家具の壁際へのドラッグと内側への復帰を確認します。共同編集ではサーバーも同じ規則を適用する必要があります。実バックエンドとの結合は未確認です。

## 共有リンク・共同編集UI（Issue #8）

「部屋を共有」から編集用リンクの作成・コピー、共有リンクからの参加、接続・同期状態と参加人数の確認、共同編集からの退出ができます。家具の選択・視点・寸法表示は各画面で独立し、間取りと家具の配置を共有する構成です。

**今回の実装はフロントエンドのみです。同期APIが未実装のため、現状では別端末間の共同編集は利用できません。** API未設定時はリンクの新規作成を無効にし、個人編集を継続できます。リンク発行や同期の成功を疑似的に表示する処理はありません。

API提供後に`.env.local`の`VITE_ROOM_API_URL`を設定してください。必要なHTTP API・SSEの形式、同時編集と再接続の扱いは[共同編集APIの接続仕様](docs/collaboration-api.md)に記載しています。

`room-session.js`が確認済みスナップショットと未確定操作を管理し、別の参加者の変更を受け取っても自分の未確定操作を維持します。切断中は編集を一時停止し、復帰時に未確認操作を再送します。間取り変更によって無効になった操作は破棄し、共有から退出すると未送信操作を破棄して最後に確認した配置の個人編集に切り替えます。

`npm test`（ユニットテスト）はドラッグの回帰テストに加え、リンク生成・API通信・同時変更・再接続・操作の重複防止・退出を検証します。ユニットテストの2クライアント検証はテスト内のAPIアダプターを使用します。ブラウザ操作の検証は以下のE2Eで行います。

## テスト・CI

以下は`frontend/`で実行します。

```bash
npm ci

# ユニットテスト（Node.js標準のnode:test）
npm run test:unit

# 初回のみ: E2E用Chromiumと必要なLinuxライブラリを準備
npm run test:e2e:install

# デスクトップ幅・モバイル幅のUI E2E
npm run test:e2e

# 一つのプロジェクトだけ実行
npm run test:e2e -- --project=desktop

# Playwrightの対話モード（ブラウザ経由。Codespacesでも利用可能）
npm run test:e2e:ui

# 実行結果のHTMLレポート
npx playwright show-report
```

ユニットテストは`src/features/*/utils/__tests__/*.test.js`を探索します。配置更新・初期家具・スナップショットの検証・ドラッグ・API・共有セッションを対象とします。UI E2Eは`e2e/*.spec.js`に配置し、間取り切り替え、家具の追加・数値/色編集・回転・削除、デスクトップでの3Dドラッグ、共有ダイアログ、クリップボード失敗、2ブラウザコンテキストでの同期、切断後の再送、存在しない部屋、共有作成失敗、個人配置の保存・復元・消去・保存領域のエラーと共有データの分離を確認します。

E2Eは本番ビルドを一度だけ`dist-e2e/app/`へ作成し、実行時設定でAPIの有効・無効を切り替えます。Viteのプレビューを4173番（API設定あり）と4174番（API未設定）、テスト専用のメモリ内APIを4175番で自動起動します。設定の混在を防ぐため既存サーバーは再利用しません。利用中の場合は停止するか、Playwright設定・テスト内URL・E2EのViteプロキシのポートを整合させてください。

`desktop`と`mobile`は3D描画モジュールだけを置換し、React UI・状態管理・HTTP/SSEを検証します。`3d`は実際のCanvas/WebGLでドラッグ、静止時の描画停止と操作時の更新、デスクトップ幅・モバイル幅での2画面同期を検証します。3DはUIの完了後に1 workerで実行し、ソフトウェア描画の競合を避けます。外部HDR環境画像は小さなRGBE画像、フォントは空のCSSへ置き換え、外部ネットワークに依存させません。共同編集では実際のHTTP/SSEでブラウザとテスト専用APIを接続しますが、APIの保存・競合処理はテスト用の簡略実装です。AWS・実サーバー・本番認証・実機タッチ操作・他ブラウザへの対応を保証するテストではありません。

失敗時のスクリーンショットとCI初回リトライのトレースは`test-results/`、HTMLレポートは`playwright-report/`に出力します。これらと`dist-e2e/`はGit管理対象外です。

[Frontend CI](../.github/workflows/frontend-ci.yml)はmainへのPR・push、および手動実行に対応します。Ubuntu 24.04・Node.js 22でユニットテストと本番ビルド、ChromiumでのUI E2Eを別ジョブとして実行し、ブラウザのレポートと失敗時成果物を7日間保存します。バックエンドの資格情報やCodespaces固有の設定は不要です。

### Chromiumを起動できず全件失敗する場合

`Executable doesn't exist`は、Playwrightのブラウザ本体が現在の保存先にないことを示します。`npm ci`だけではブラウザはインストールされません。`frontend/`で`npm run test:e2e:install`を実行し、続けて`npm run test:e2e`を実行してください。

通常はPlaywrightの標準キャッシュを使います。`PLAYWRIGHT_BROWSERS_PATH`を指定する場合は、インストール時と実行時で同じ値を使ってください。特定の開発者の`/tmp`などを設定ファイルに固定しません。`test:e2e`と`test:e2e:ui`はサーバー起動前にChromiumの起動確認を行い、準備不足の場合はセットアップ方法を表示して停止します。

通常のE2Eコマンドは実行ロックを取得し、同じ作業ディレクトリで同時に実行してトレースが削除されるのを防ぎます。終了後は自動解除し、プロセスが終了済みのロックは次回実行時に回収します。実行中に`test-results/`や`playwright-report/`を削除しないでください。

2クライアントのシナリオではゲスト画面を専用fixtureで管理し、画面離脱後の参加人数を確認してからブラウザコンテキストを破棄します。ソフトウェア3D描画の終了処理にはテスト本体とは別の時間枠を設けています。

### E2Eの性能確認

比較結果・採用理由は[改善実験の記録](docs/e2e-performance.md)を参照してください。`test-results/run-timing.json`にビルド・Playwright・合計の時間を保存します（npmとブラウザ事前確認の時間は含みません）。3Dだけを再確認する場合は`npm run test:e2e -- --project=3d --no-deps`を使います。通常の全件実行も必ず確認してください。

3D描画は`frameloop="demand"`で変更時だけ行います。新しいアニメーションや外部からの直接変更を追加する場合は、必要な`invalidate()`と停止条件を確認してください。

トレースは`on-first-retry`です。ローカルはリトライしないため、トレースで調査する場合は`npm run test:e2e -- --trace=retain-on-failure`で再現してください。スクリーンショットとHTMLレポートは通常実行でも保存します。

### CodespacesでUIモードを開く

`npm run test:e2e:ui`はUIサーバーを`0.0.0.0:8080`で起動します。Codespacesの「ポート」タブで8080番を「ブラウザーで開く」から表示してください。ポートの可視性は「Private」のまま使用します。別の端末では表示されたURLでUIを開き、テストを選んで実行できます。終了は実行ターミナルでCtrl+Cを押します。

通常の`--ui`だけではローカルのGUIブラウザを起動するため、X Serverのない環境で`Browser.getVersion` / `session closed`が発生します。ブラウザ経由のUIモードはX Serverを必要としません。8080番が使用中なら`npm run test:e2e:ui -- --ui-port=8081`のように変更し、同じ番号を転送してください。4173〜4175番は引き続きテスト用に使用します。GUIウィンドウを直接開く環境では`npm run test:e2e -- --ui`も使用できます。

この設定は[PlaywrightのCodespaces向けUIモード手順](https://playwright.dev/docs/test-ui-mode#docker--github-codespaces)に沿っています。CIは引き続き通常のヘッドレスE2Eを実行します。

クリップボードの成功ケースはテスト対象originだけに権限を与え、対象ページをアクティブにして実際の読み書きを確認します。拒否ケースは`writeText`の拒否を再現し、案内・フォーカス・リンク全文の選択範囲をリトライ付きアサーションで検証します。UIモードでタイムアウトした場合は、クリップボードの権限エラーか、準備や選択範囲確認の待機かをトレースで確認してください。

実3Dで画面座標を投影するテストでは、初期描画が落ち着くまで`waitForSceneToSettle`で描画回数の安定を確認します。最初の描画だけでは家具やカメラの更新が完了していない場合があるためです。操作時は対象家具の選択も確認し、固定秒数の待機や失敗のリトライ増加では対処しません。

取込間取りの家具は回転後の外形が1枚の床ポリゴンに収まり、描画される壁ボックスと重ならない位置へ配置します。扉の開口と家具の高さも判定します。ドラッグで壁に触れた場合は壁へ向かう成分だけ補正し、壁沿いには移動できます。要求位置が壁の反対側で完全に収まれば、その位置へ移動できます。数値入力や回転で壁に重なる場合は直前の配置を維持します。追加時だけ配置できる位置を探索し、見つからなければメッセージを表示します。複数の床をまたぐ配置、家具同士の衝突判定には未対応です。床は認識した部屋の境界ではなく仮の長方形です。

同じ図面のサイズ補正は家具の寸法・位置を維持し、補正後に床や壁へ収まらない家具があれば適用を拒否します。新しく画像を解析して適用すると、家具を空にして間取りを置き換えます。

## 平面図と視点（Issue #19）

プレビュー上部の「平面図」で、床・壁・家具の外形と名前を図面として表示します。家具のクリック・Enter/Spaceでの選択、ドラッグ、既存の追加・数値編集・回転・色変更・削除が使えます。「3D」で立体表示、「初期視点」で従来の視点、「正面」で+Z側からの表示に切り替えます。切り替えても配置と選択は維持し、表示モード・視点は共同編集相手へ送信せず個人保存にも含めません。3Dへ戻ると最後に指定したプリセットで表示します。

平面図には実寸に対応するグリッドを表示します。通常の大きさでは1目盛0.25m・太線1mで、大きな間取りは線が密集しないよう間隔を広げます。取込間取りの扉は壁の隙間、窓は青い帯です。壁・床・開口は「図面モード」で修正できます。平面図のパン・ズームは未対応です。参考例・方式比較・制約は[表示方式の調査](docs/view-mode-research.md)を参照してください。

Floorplanner・Sweet Home 3Dの間取り取り込み、共同編集の確認範囲と導入候補は[競合機能の調査](docs/floorplanner-sweethome3d-research.md)を参照してください。

## 下絵を使った図面編集（Issue #50）

画像変換後は元画像を下絵にして図面モードで編集できます。保存後は「図面の新規作成・読込・画像変換」の「手直し用の下絵」で同じ画像を再選択してください。再選択だけでは解析や形状の置換をせず、縦横比の異なる画像は拒否します。同じ画像かどうかは自動判定しないため、切り抜きや回転をしていない画像を使います。下絵の表示・濃さを変更でき、位置・縮尺は固定です。

- 「選択・頂点を動かす」で壁・床・開口を選び、白い点をドラッグ・矢印キーで動かします。通常0.01m、Shift＋矢印キーは0.1mです。
- 「壁を追加」で2点を指定します。「線を消す」は壁1本と付属の開口を削除します。グリッドは目安で、自動吸着はしません。
- 床の頂点移動・各辺への頂点追加・削除に対応し、自己交差や3点未満の床は拒否します。
- 「扉を追加」「窓を追加」で同じ壁上の2点を指定し、選択した開口の端点移動や削除もできます。壁外・重複・幅0.1m未満の開口は拒否し、既存の高さを維持します。開き勝手は未対応です。
- 局所Undo/Redoは最大100操作です。一連のドラッグは1操作で、キャンセル・フォーカス喪失では開始前へ戻ります。Escは操作途中の点指定・ドラッグを中断します。保存・モード切替を越える履歴の永続化はしません。

図面の形状検証と3Dへ反映する際の家具検証は分けます。家具と重なる壁を図面として保存することはできますが、そのまま3Dへ反映することは拒否し、既存の家具や個人配置保存を維持します。

図面の設計と関連Issueへの影響は[図面モードの設計](docs/drawing-mode.md)、今後の図面要件は[要件整理](docs/plan-view-requirements.md)を参照してください。

### 新しい図面と同じ図面の修正の区別

図面ごとのIDと3D配置の元図面IDを比較して家具の引き継ぎを決めます。別画像の取り込み・新規作成では新しいIDを発行し、同じ図面の手直し・サイズ補正では維持します。JSONファイルもIDを持ち、同じ図面の開き直しでは家具を維持します。IDのない旧JSONは新しい図面として開きます。保存・再読込後も区別を維持し、保存領域の拒否時も画面内で編集できます。

既存のIDなしの個人配置は、元形状から移行用IDを作って同じ図面の編集として開きます。読み込みだけでは書き込みません。旧形式の図面と配置の対応が不明な場合は家具の保護を優先します。修正前に取り込んだ別画像で家具エラーが残る場合は、画像を再選択して新しい図面へ変換してください。
